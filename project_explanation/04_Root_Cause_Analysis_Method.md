# 04 — Root Cause Analysis Method: IncidentIQ

## 1. Analysis Pipeline (13-Step Deterministic Flow)

IncidentIQ implements an explainable, deterministic investigation pipeline:

```
[Uploaded Evidence]
       │
       ▼
 1. Load & Validate Schemas
       │
       ▼
 2. Normalize Timestamps to UTC (ISO 8601)
       │
       ▼
 3. Map to Target Canonical Schema
       │
       ▼
 4. Preserve Provenance (Source File + Row Index)
       │
       ▼
 5. Group by Timestamp, Service, & Trace ID
       │
       ▼
 6. Build Unified Chronological Incident Timeline
       │
       ▼
 7. Detect Patterns (Errors, Timeouts, Saturation)
       │
       ▼
 8. Resolve Service Topology & Call Hierarchy
       │
       ▼
 9. Generate Candidate Root-Cause Hypotheses
       │
       ▼
10. Evaluate Supporting & Contradicting Evidence
       │
       ▼
11. Compute Explainable Heuristic Support Score
       │
       ▼
12. Formulate Grounded Remediation Next Checks
       │
       ▼
13. Check Abstention Criteria & Output Documented Limits
```

---

## 2. Explainable Heuristic Scoring Model

IncidentIQ explicitly differentiates between a **heuristic evidence score** and a **statistically calibrated probability**. A heuristic score reflects the degree to which uploaded telemetry supports a specific hypothesis.

### Mathematical Formulation:

$$\text{Score} = \text{clamp}\Big(0.05,\, 0.96,\, \text{Base} + (w_t \cdot C_t) + (w_e \cdot C_e) + (w_c \cdot C_c) - (w_p \cdot C_p)\Big)$$

Where:
- $\text{Base} = 0.15$: Minimum prior baseline for an observed hypothesis.
- $w_t = 0.25$: Weight for **Temporal Match** ($C_t \in [0, 1]$). Measures whether the event (e.g. deployment) occurred within 60 minutes prior to error onset.
- $w_e = 0.30$: Weight for **Error Density** ($C_e \in [0, 1]$). Ratio of 5xx errors and critical exceptions recorded in the incident window.
- $w_c = 0.25$: Weight for **Causal / Topological Link** ($C_c \in [0, 1]$). Confirms direct dependency between failing upstream caller and downstream target.
- $w_p = 0.35$: Weight for **Contradiction Penalty** ($C_p \in [0, 1]$). Deductions applied when telemetry weakens the claim.

### Confidence Tiers:
- **High evidence support:** $\text{Score} \ge 0.75$
- **Moderate evidence support:** $0.50 \le \text{Score} < 0.75$
- **Low evidence support:** $0.25 \le \text{Score} < 0.50$
- **Insufficient evidence:** $\text{Score} < 0.25$

## 3. Evidence Provenance & Grounding

Every citation generated by the engine includes:
- `file_name`: Original name of the uploaded file.
- `row_number`: 1-based original line index from the file.
- `timestamp`: UTC timestamp.
- `service`: Emitting microservice.
- `summary`: Concrete explanation of why this record is relevant.

**No invented IDs or synthetic recovery timestamps are ever generated.**

---

## 4. Contradiction Detection

A core tenet of the scientific method is attempting to *falsify* candidate hypotheses. IncidentIQ actively inspects records for contradictory evidence:

- **Temporal Order Violation:** If application errors began *before* a deployment was rolled out, a severe contradiction penalty is applied.
- **Healthy Metric Counter-Evidence:** If a database crash is suspected, but database metrics show CPU < 20% and zero active query locks, this is flagged as contradictory evidence.

---

## 5. Uncertainty & Engine Abstention

When uploaded telemetry is sparse, contradictory, or absent during the critical onset window, the engine **refuses to produce a false conclusion**.

### Abstention Triggers:
1. Total evidence records $< 4$.
2. Zero error signals across all uploaded logs and metrics.
3. Telemetry timestamp range does not overlap with the reported incident window.

When triggered, the engine returns a score of $0.10$ and states:
> *"Insufficient evidence to rank a root cause reliably."*

It accompanies this abstention with a specific **diagnostic data checklist** detailing what logs, metrics, or traces must be collected to resolve the incident.
